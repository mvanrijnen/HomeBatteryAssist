# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HomeBatteryAssist is a **Home Assistant custom integration** (not an add-on/Docker container), distributed via HACS, that monitors home batteries and the energy flows of a home, and forecasts consumption, prices, PV and battery behaviour (read-only; forecasts are verified afterwards). Comparable project: Omnibattery (`ffunes/Omnibattery`).

- **Read-only, by decision of the project owner: HomeBatteryAssist never controls batteries or any other device** — no commands, no state-changing service calls, no control configuration, no own connections to devices that could compete with their integrations (e.g. Marstek Venus v3 allows only one Modbus TCP client; Omnibattery must keep running). Exception agreed by the owner: grid meters may be read directly when that is passive or uses a read-only interface open to any number of clients, and never changes a meter setting (`inputs/direct.py`: HomeWizard P1 API v1, SMA Speedwire multicast). Scope: read inputs, forecast, and verify forecasts afterwards against what actually happened.
- Domain `homebatteryassist`, display name **HomeBatteryAssist**, single config entry (`single_config_entry` in manifest).
- Built incrementally. Batteries are linked through entities of their own integration (`inputs/batteries.py`), helped by profiles that recognise batteries other integrations already expose (`inputs/profiles.py`). Network discovery of devices is deferred.
- Forecasts are **not** made by this integration; it consumes them from other integrations.
- Will be published: keep README, user-facing text and translations release-quality. Repo: https://github.com/mvanrijnen/HomeBatteryAssist (public, alpha: no GitHub releases until the user says so; branch `main`). License: MIT (`LICENSE`).

## Architecture

The integration is split into modules with a one-way data flow. Keep new code in the right module and do not import "upstream" (e.g. `inputs` must not import `forecasts` or `output`):

```
inputs  ->  history  ->  forecasts  ->  (planning, later)  ->  output
explain (decision log, "why") and Python logging are used by all modules
```

`__init__.py` only wires the modules of a config entry into `HomeBatteryAssistData` (`models.py`, on `entry.runtime_data`): `decisions`, `measurements`, `history`, `forecast`. Root platform files (`sensor.py`, `button.py`) only delegate to `output/`, because HA looks for platforms in the package root. `async_setup` registers the action `homebatteryassist.recalculate` (`services.py`) and the sidebar panel (`output/panel.py` + `frontend/panel.js`, websocket `homebatteryassist/status`) once per HA start; note HA only runs `async_setup` when a config entry exists (or YAML), so the panel appears after the integration is added. The panel shows a "not set up" hint if the entry is not loaded.

- **`inputs/`** — reads and normalises external data; never forecasts or decides.
  - `units.py`: `state_to_watts` (W/kW/MW, A/mA × `NOMINAL_VOLTAGE` 230 V), `parse_time`, `parse_float`.
  - `measurements.py`: `MeasurementInput`, event-driven (state change listener, no polling). `house = Σ grid phases + Σ PV sources − Σ excluded loads − Σ battery power`, floored at 0 W. Grid per phase: one signed sensor (+import/−export) or import minus optional separate return sensor; PV/excluded use absolute values. Unknown grid sensor → consumption unknown (`missing` lists them); unknown PV/excluded → 0 W. Listeners receive `(time, power)`.
  - `prices.py`: `parse_price_forecast` reads a price sensor's attributes in common formats (lists of dicts with start/end/price-like keys under `prices`, `raw_today`/`raw_tomorrow`, `forecast`, ...; or `{timestamp: price}`). Unit = the source sensor's unit.
  - `batteries.py`: `BatteryConfig` (from a `battery` subentry), `BatteryState` (soc, `power_w` normalised to **+ charging / − discharging**, status, stored/usable/room kWh, time to full/empty), `BatteryInput` (state listener, persisted kWh counters and last full charge in `.storage/homebatteryassist.<entry_id>.batteries`, decision log on lost/restored/full charge).
  - `profiles.py`: `BatteryProfile` per known integration (platform + entity translation keys → subentry fields); `find_battery_candidates` scans the entity registry (never the network) for not-yet-linked batteries and reads starting values from their states. Verified profiles: `omnibattery` and `marstek_modbus` (power = `ac_power`, + discharging). Only add profiles whose keys were verified on a real installation.
  - `meters.py`: `MeterProfile` per known grid meter integration (marker translation key that only grid meters have + signed phase power key, phase from the unique id); `find_meter_candidates` scans the entity registry. Verified: `homewizard` P1 (`dsmr_version`, `active_power_phase_w`, `_active_power_l<n>_w`). Config flow step `meter` (only if one is found) fills phases + sensors; manual sensors always remain possible.
  - `direct.py` + `speedwire.py`: grid meters read directly about every second (`entry.data` `meter_source` = `homewizard` (P1 + kWh meters, verified) | `speedwire` (SMA, verified) | `shelly` | `shelly_em` | `iammeter` (these three from API docs, unverified), `meter_address`); candidates from config entries/device registry (`find_direct_meters`), or entered by address (flow step `direct`); `MeasurementInput` then takes the phases from the meter, not from sensors, and entity listeners (`entity=True`) are throttled to 10 s to spare the recorder. Speedwire discovery in the config flow only listens (3 s; patched out in tests, sockets are blocked). History import needs `source_entity` then.
  - `price_drivers/`: `PriceDriver` (find sources / async_read(source, role import|market|export) / watch); `DRIVERS` registry; `template.py` is a code example only (never registered). DynTarNL verified; core action drivers (Nord Pool, Tibber, EnergyZero, easyEnergy, cached 1 h) and HACS sensor-attribute drivers (offered only if their attributes parse) unverified. Options `price_source` (`<driver>:<source>` or `sensor` = `price_forecast_entity`), `price_extension` (extra forecast, merged after, estimated).
  - `battery_drivers/` (telemetry via entities by translation key; Omnibattery + Marstek Modbus verified for reading; write methods exist but are NEVER called — read-only), `meter_drivers/` (registry over `direct.py` meters; also PV sources: subentry `pv_driver` + `pv_address`); each with a `template.py` code example that is never registered.
  - `solar.py`: PV forecast via the Energy dashboard solar forecast platform (`<domain>/energy.py` → `async_get_solar_forecast` → `wh_hours`); multiple entries summed per hour.
- **`history/`** — `importer.py` (action `import_history`: reconstruct past consumption from recorder statistics with the live formula, or take over a sensor; records marked `source: import`; own measurements win), `profile.py` (hourly series and day profile for the dashboard). `ConsumptionHistory`: time-weighted average per clock-aligned interval (5/15/60 min), own boundary timer, `Store` `.storage/homebatteryassist.<entry_id>.consumption`, pruned after 28 days, `coverage` per record. Roll-over is idempotent and handles late/missed boundaries; gaps count as unmeasured. Records also keep `excluded_w` (excluded devices), `pv_w` (measured PV) and `battery_w` (+ charging). Basis for the consumption forecast.
- **`forecasts/`** — derived knowledge about the future.
  - **Rule: every forward-looking calculation first determines the `PlanningWindow` and never calculates beyond `window.end`.** New forecast/planning code takes the window as a parameter (use `window.slots(step)` / `window.overlaps(start, end)`), and does nothing when `window.is_empty`.
  - `horizon.py`: `planning_horizon` → `PlanningWindow(start=now, end, limited_by: HorizonLimit)`, end = min(now + configured days, price end, PV end); a configured forecast without future data → empty window (`NO_PRICE`/`NO_PV`). Exposes `hours`, `duration`, `slots()`, `overlaps()`.
  - `coordinator.py`: `ForecastCoordinator` (`DataUpdateCoordinator`; interval option `forecast_interval` 5/15/30/60 min, default 15; also on price-sensor change and the recalculate action/button) runs each cycle in fixed order: 1) read inputs, 2) determine the window, 3) calculate/clip everything to the window incl. the consumption forecast, 4) record predictions and verify measured slots. `ForecastData.prices`/`pv_wh`/`consumption` are limited to the window; `price_end`/`pv_end` show how far the raw inputs reach. Fires `homebatteryassist_forecast_updated`.
  - `consumption.py`: `ConsumptionProfile` = recency-weighted (half-life 14 d) mean per local weekday+hour, falling back to weekday/weekend+hour, hour, overall (each level needs ≥ 2 distinct days). `forecast_consumption` → `ForecastSlot`s per history-interval slot of the window.
  - `adjustments.py`: user adjustments (`factor`, `offset_w`, `power_w`) per period, persisted (`.adjustments` store), applied power → factor → offset, weighted by overlap. Set via actions `adjust_forecast` / `clear_forecast_adjustments`.
  - `accuracy.py`: `ForecastAccuracy` — running accuracy of the consumption, PV and price forecasts per lead-time bucket (0-1h … 5d+): raw predictions are recorded per slot and settled against measured consumption (own records), measured PV (`pv_w` in history, per hour) and later-published prices; exponentially weighted (half-life 7 d) MAE/bias/MAPE; corrections (consumption/price additive, PV factor 0.5–1.5) grow to full strength at `MIN_SAMPLES`. Always learn from **raw** predictions. Per kind a user-controllable mode (`learned`/`off`/`manual` per bucket, optional duration) via actions `set_forecast_correction` / `reset_forecast_accuracy`. Consumption order: profile → correction → user adjustments.
- **Phase limits** — `planning/phase_limit.py`: max power per phase = `max_current_per_phase` × 230 V × (1 − `phase_margin` option / 100; % of the fuse, default 10); batteries/PV/excluded loads have a `phase` (`none` = spread evenly, 1-phase = all on L1). `forecasts/phases.py` `PhaseProfile` learns the house/PV share per phase from history records (`phase_house_w`, `phase_pv_w`, per local hour; even split without history) → per-slot `limits` for `plan_batteries` (slots marked `limited`, mentioned in the story). The virtual battery simulator caps live on the measured phase power (`cap_powers`) and logs `phase_limit` / `phase_limit_cleared`. Phase protection: on an overloaded phase (by itself) its virtual batteries take load off it (`relieve`, overrides the plan; `phase_relief` / `phase_relief_ended`), and the simulator also steps right away on a measurement that shows an overload (max every 2 s).
- **Plan check** — `planning/verification.py` `PlanVerification`: per history-interval slot the selected plan at slot start (power, expected saving via `slot_saving`) vs the batteries' counters (charged/discharged kWh, `value`) over the slot; per-day summary on the dashboard; store `.plan_check`; settled by a boundary timer in `__init__.py`.
- **`output/`** — entities. `batteries.py`: one device per battery subentry (entities added with `config_subentry_id`, unique id `<subentry_id>_<key>`) plus `batteries_*` totals on the main device (only if batteries exist). `sensors.py`: `House consumption` (W), diagnostic `Planning horizon` (timestamp = window end; attributes `hours_ahead`, `days_ahead`, `limited_by`, ...), `Last decision` (explanation; `recent` attribute). Common base `HomeBatteryAssistEntity` (one service device, unique id `<entry_id>_<key>`, translation key = key).
- **`explain/`** — the decision log ("why"), separate from technical logging. `DecisionLog.async_log(category, key, **params)` renders a message from `messages.py` in `hass.config.language` (nl/en, fallback en), persists the last 200 (`.storage/homebatteryassist.<entry_id>.decisions`), logs it at INFO, fires event `homebatteryassist_decision`, and notifies the `Last decision` sensor. Log only *changes* worth explaining (e.g. horizon limit changes, measurement lost/restored — not the first state after start-up). Every message key must exist in all languages (tested).
- **Icons** — `brand/icon.png` (+ `@2x`, `dark_`) is served by HA's brands integration for this custom integration; `icons.json` gives every entity/action an MDI icon (no `_attr_icon` in code). `images/icon.png` is the README copy; regenerate all from the same design.
- **Technical logging** — `_LOGGER = logging.getLogger(__name__)` in every module (so users can set levels per module); details at DEBUG. `diagnostics.py` provides the diagnostics download with config and the state of each module.

### Configuration model

- `entry.data` (fixed, config flow steps 0–3; step 0 `meter` only when a known meter is detected): `phases` (1/3); `max_current_per_phase`, restricted by `MAX_CURRENT_OPTIONS` (1x10/25/35A, 3x25/35/50/63/80A; defaults 1x35A, 3x25A); `sensor_l1..l3` + optional `return_l1..l3`.
- `entry.options` (step 4 `settings` and the options flow, same `settings_schema`): `history_interval`, `planning_horizon_days` (1–7, default 2), optional `price_forecast_entity`, optional `pv_forecast_entries` (list of config entry ids; field only shown if a solar forecast integration is loaded).
- Subentries (any number, added under the integration in the UI, with reconfigure): `pv_source` and `excluded_load` (e.g. EV charger) with `name`, `sensor`, `phase` (`none`/`l1`–`l3`; field only on 3-phase); `battery` with step `user` (pick a detected battery or `manual`; skipped when nothing is detected) → `battery` (sensors and properties, prefilled from the profile); reconfigure uses the battery form. `sensor_conflict` ensures every sensor is used once (grid or one subentry).
- Any options or subentry change reloads the entry (update listener). Unload awaits `HouseConsumption.async_stop()` so history is saved before the reload reads it.
- Every new config text must be added to `strings.json`, `translations/en.json` (identical copy) and `translations/nl.json`. Custom integrations can't use `[%key:...%]` references — write literal text.

## Commands

Home Assistant's test harness does not run on native Windows (`fcntl`); on Windows, lint and test in WSL. Machine-specific paths and live-instance details are in `CLAUDE.local.md` (not committed).

```bash
python -m venv .venv && .venv/bin/pip install -r requirements_test.txt   # Linux/WSL/macOS
ruff format . && ruff check .
pytest -q                                                       # all tests
pytest -q tests/test_forecast.py::test_planning_horizon_end     # single test
```

CI (`.github/workflows/validate.yml`) runs hassfest, HACS validation, ruff and pytest on Python 3.14. `hacs.json` declares minimum HA 2025.6.0 (needed for config subentries).
