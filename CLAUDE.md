# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HomeBatteryAssist is a **Home Assistant custom integration** (not an add-on/Docker container), distributed via HACS, that monitors home batteries and the energy flows of a home, and forecasts consumption, prices, PV and battery behaviour (read-only; forecasts are verified afterwards). Comparable project: Omnibattery (`ffunes/Omnibattery`).

- **Read-only, by decision of the project owner: HomeBatteryAssist never controls batteries or any other device** — no commands, no state-changing service calls, no control configuration, no own connections to devices that could compete with their integrations (e.g. Marstek Venus v3 allows only one Modbus TCP client; Omnibattery must keep running). Exception agreed by the owner: grid meters may be read directly when that is passive or uses a read-only interface open to any number of clients, and never changes a meter setting (`engine/devices/meters/discovery.py`: HomeWizard P1 API v1, SMA Speedwire multicast). Scope: read inputs, forecast, and verify forecasts afterwards against what actually happened.
- Domain `homebatteryassist`, display name **HomeBatteryAssist**, single config entry (`single_config_entry` in manifest).
- Built incrementally. Batteries are linked through entities of their own integration (`engine/measure/battery_monitor.py`), helped by profiles that recognise batteries other integrations already expose (`engine/devices/batteries/recognition.py`). Network discovery of devices is deferred.
- Forecasts are **not** made by this integration; it consumes them from other integrations.
- Will be published: keep README, `docs/` (details per topic; README is the overview with links), user-facing text and translations release-quality. Repo: https://github.com/mvanrijnen/HomeBatteryAssist (public, alpha: no GitHub releases until the user says so; branch `main`). License: MIT (`LICENSE`).

## Architecture

The package root holds what Home Assistant needs (`__init__.py`, `config_flow.py`, `services.py`, `diagnostics.py`, platform files, `output/` entities, `frontend/` panel, translations). All backend logic is in **`engine/`**, organised in layers with a one-way data flow (`docs/architecture.md`). A layer only imports lower layers:

```
engine/devices (1) -> engine/sources (2) -> engine/measure (3) -> engine/history (4)
  -> engine/forecast (5) -> engine/planning (6) -> engine/evaluation (7)
engine/explain (8) is used by all; engine/coordinator.py runs one forecast cycle
```

**Devices are drivers** (`engine/devices/`, part of the code; one file per brand / type); **everything else that is swappable is a module** (built-in in its layer, own ones loaded from `/config/homebatteryassist/<kind>/` by `engine/own_modules.py`, keyed `custom_<key>`). Every extension point has `base.py` (interface), `template.py` (example, never registered) and one file per built-in variant.

`__init__.py` only wires the parts of a config entry into `HomeBatteryAssistData` (`models.py`, on `entry.runtime_data`). Root platform files (`sensor.py`, `button.py`) only delegate to `output/`. `async_setup` registers the actions (`services.py`) and the sidebar panel (`output/panel.py` + `frontend/panel.js`, websockets `homebatteryassist/status` and `/history`) once per HA start; HA only runs `async_setup` when a config entry exists, so the panel appears after the integration is added.

- **1 `engine/devices/`** — drivers, read-only.
  - `batteries/`: `base.py` = `BatteryModel` (a type by inheritance brand → range → type, e.g. `marstek/__init__.py` → `marstek/venus.py` → `marstek/venus_e_v3.py`; specs used as starting values; `MODELS`, `model_for(device model)`) and `BatteryReader` (one integration's entities, `integrations/omnibattery_integration.py`, `integrations/marstek_modbus_integration.py`, verified; its `BatteryProfile` recognises batteries; telemetry by translation key; write methods exist but are NEVER called). `recognition.py` `find_battery_candidates` scans the entity registry (never the network). `virtual.py` = the virtual battery simulator (follows the plan; phase protection `relieve`, phase caps `cap_powers`, peak shaving).
  - Direct battery drivers (PREPARED, NOT USED; `enabled = False`, never offered, write methods never called): `batteries/direct/` (`DirectBatteryDriver`, `modbus_driver.py` `ModbusBatteryDriver` with `Point` register maps, `http_driver.py` `HttpBatteryDriver`, `mqtt_driver.py` `MqttBatteryDriver`), one per brand next to its models (`marstek/venus_direct_modbus.py`, `anker/solarbank_direct_modbus.py`, `huawei/sun2000_direct_modbus.py`, `zendure/solarflow_direct_http.py`, `sessy/sessy_direct_http.py`, `indevolt/flex_direct_http.py`, `hoymiles/smiles_direct_mqtt.py`; `DIRECT_DRIVERS`); own Modbus TCP client `devices/transports/modbus_tcp.py`. Device facts from Omnibattery (GPL-3.0) as facts only — never copy its code (HBA is MIT). Each driver declares its control needs (`refresh_s`, `min_interval_s`, `deadband_w`, `idle_is_release`, limits).
  - `meters/`: one file per brand — `homewizard.py` (P1 + kWh, API v1, verified), `sma.py` (Speedwire multicast, receive only, verified; discovery only listens 3 s, patched out in tests), `shelly.py`, `iammeter.py` (from API docs, unverified); `direct_reading.py` = `DirectMeter`/`PollingMeter` (stale after 10 s → listeners told); `discovery.py` = `find_direct_meters` / `create_meter`; `__init__.py` `DRIVERS` (also PV sources: subentry `pv_driver` + `pv_address`); `via_ha_integration.py` = meters via their HA integration (`MeterProfile`, HomeWizard P1 verified; config flow step `meter`).
- **2 `engine/sources/`** — modules for external data.
  - `prices/`: `PriceDriver` (find sources / async_read(source, role import|market|export) / watch), `DRIVERS`; `price_points.py` = `PricePoint` + `parse_price_forecast`; DynTarNL verified; action drivers (Nord Pool, EnergyZero, easyEnergy, cached 1 h) and sensor-attribute drivers unverified; `in_development/` (e.g. Tibber) is never offered. Options `price_source` (`<driver>:<source>` or `sensor`), `price_extension`.
  - `pv_forecasts/`: `PvForecastSource`; `solar_forecast_integrations.py` wraps `energy_dashboard_platform.py` (Energy dashboard solar forecast platforms); option `pv_forecast_entries` holds `<key>:<id>` or a plain config entry id (= energy); final check drops invalid values.
  - `weather/` (optional): `WeatherSource`; `ha_weather_entity.py` reads a weather entity (`temperature` attribute, `weather.get_forecasts`, read-only, cached 30 min) as °C per UTC hour. Options `weather_entity`, `outdoor_temperature_sensor`.
  - `tariffs/`: `Tariff` turns source prices into what a kWh costs/earns (`apply_tariff`, after the window/correction step, before planning; market prices when `needs_market`); price accuracy stays on source prices.
- **3 `engine/measure/`** — `house_measurement.py` `MeasurementInput` (event-driven): `house = Σ grid phases + Σ PV − Σ excluded − Σ battery power`, floored at 0; grid per phase from sensors (signed, or import − return) or a direct meter (entity listeners throttled to 10 s); unknown grid → consumption unknown. `battery_monitor.py`: `BatteryConfig`, `BatteryState` (`power_w` **+ charging / − discharging**), `BatteryInput` (counters, realised value incl. `value_kwh` for wear, last full charge, activity explanations as periods, one message after start-up). `spike_filters/` = spike filter modules (`SpikeFilter.update(when, house_w)` -> `SpikeState(ignore_w, ended_wh)`, stream with own state, `checked` final check; built-in `short_peaks`: rise > threshold above a slow baseline, over within max duration; own ones in `/config/homebatteryassist/spike_filters/`), run by `MeasurementInput`; `nom_balance` = what NOM asks of the batteries (never discharges for excluded devices or ignored peaks). `history/spikes.py`: `spike_w` per record, regular peaks (weekday+hour, ≥ half of the days in 4 weeks) stay in the average and are covered; options `spike_no_discharge`, `spike_exclude_average` (both default on), `spike_threshold_w`, `spike_max_minutes`, `spike_filter`. `engine/units.py`: `state_to_watts`, `parse_float`, `parse_time`.
- **4 `engine/history/`** — `consumption_history.py` `ConsumptionHistory` (time-weighted average per clock-aligned 5/15/60-min interval, `coverage`, `excluded_w`, `pv_w`, `battery_w`, phases; 28 days; invalid stored records skipped), `history_import.py` (action `import_history`), `weekday_hour_profile.py` (charts).
- **5 `engine/forecast/`** — **every forward calculation first determines the `PlanningWindow` (`planning_window.py`) and never calculates beyond `window.end`.** `consumption_forecast.py` runs the chosen consumption forecaster module (`forecasters/`: `weekday_hour_profile.py` recency-weighted weekday/hour profile, `same_time_last_weeks.py` last weeks; `raw_forecast` replaces invalid values by the profile) → temperature step (`temperature_effect.py`, optional: W per heating/cooling degree learned from daily means, heating point = room − learned gain, per zone (`measure/heating_zones.py`: heating/cooling subentry with optional `indoor_temperature_sensor`/`outdoor_temperature_sensor`, history `zones`) or the house; applied as the difference with the last week's usual degrees; skipped when a forecaster sets `uses_temperature`) → correction → user adjustments (`user_adjustments.py`); `phase_shares.py` learns the phase shares.
- **6 `engine/planning/`** — planner modules (`planners/`: `zero_on_meter.py` nom/manual/time_slots via `follow`, `arbitrage.py` DP with fractional-level discharge, cycle limit, peak shaving). `battery_plan.plan_batteries` builds `planner_input` and **always** runs `finalise` (power/phase limits, min/max SoC, price rules except user-set fixed actions; SoC/grid/costs). Then `full_charge.py` inserts periodic full charges. `phase_limit.py` (fuse × 230 V × (1 − margin)), `battery_distribution.py` (several batteries), `time_slots.py` (time slots). Failing own planner → `planner_failed`, nom used (`plan_fallback`, `ForecastData.selected_plan`).
- **7 `engine/evaluation/`** — `forecast_accuracy.py` `ForecastAccuracy` (raw predictions per lead-time bucket settled against measured consumption, PV and later prices; half-life 7 d; learned/off/manual corrections; extra kinds `consumption@<key>` per forecaster and `pv@<key>` per PV correction for the comparison tables); `pv_corrections/` = PV correction modules (`PvCorrector`, `apply_pv_correction` with final check; built-in `hour_and_level` (default: lead factor × per local hour × per level vs the most forecast at that hour) and `lead_time` (original); own ones in `/config/homebatteryassist/pv_corrections/`; option `pv_corrector`; manual/off correction mode → lead time only); `plan_check.py` (plan per slot vs the battery counters, both after wear).
- **8 `engine/explain/`** — `DecisionLog` (messages in `messages.py` incl. `TERMS` phrases, nl/en, every key in all languages — tested; last 200 persisted; event `homebatteryassist_decision`), `plan_story.py` (the plan as periods, compared with no battery), `notifications.py`.
- **`engine/control/`** — BUILT, NOT ACTIVE: `battery_controller.py` (`BatteryController`, pure `decide()`): master switch off by default (`ControlDisabled`), always release (stop/error/watchdog 2 min/switch-off), refresh, throttle + deadband, idle = release, limits. Nothing creates or enables a controller.
- **`engine/coordinator.py`** — `ForecastCoordinator` runs a cycle: read inputs, window, accuracy, consumption, tariff, plans of every mode/planner, full charges, explanations; `price_log` for the chart.
- **`output/`** — entities (battery devices per subentry, totals, sensors) and `panel.py` (websocket data for the dashboard).
- **Icons** — `brand/icon.png` (+ `@2x`, `dark_`); `icons.json` gives every entity/action an MDI icon. `images/icon.png` is the README copy.
- **Technical logging** — `_LOGGER = logging.getLogger(__name__)` everywhere; `diagnostics.py` includes the state of each part and the active/own modules.

### Configuration model

- `entry.data` (fixed, config flow steps 0–3; step 0 `meter` only when a known meter is detected): `phases` (1/3); `max_current_per_phase`, restricted by `MAX_CURRENT_OPTIONS` (1x10/25/35A, 3x25/35/50/63/80A; defaults 1x35A, 3x25A); `sensor_l1..l3` + optional `return_l1..l3`.
- `entry.options` (step 4 `settings` and the options flow, same `settings_schema`): `history_interval`, `planning_horizon_days` (1–7, default 2), optional `price_forecast_entity`, optional `pv_forecast_entries` (list of config entry ids; field only shown if a solar forecast integration is loaded).
- Subentries (any number, added under the integration in the UI, with reconfigure): `pv_source`, `excluded_load` (e.g. EV charger) and `heating_cooling` (part of the house, recorded apart as `heating_w`) with `name`, `sensor`, `phase` (`none`/`l1`–`l3`; field only on 3-phase); `battery` with step `user` (pick a detected battery or `manual`; skipped when nothing is detected) → `battery` (sensors and properties, prefilled from the profile); reconfigure uses the battery form. `sensor_conflict` ensures every sensor is used once (grid or one subentry).
- Any options or subentry change reloads the entry (update listener). Unload awaits `HouseConsumption.async_stop()` so history is saved before the reload reads it.
- Every new config text must be added to `strings.json`, `translations/en.json` (identical copy) and `translations/nl.json`. Custom integrations can't use `[%key:...%]` references — write literal text.

## Commands

Home Assistant's test harness does not run on native Windows (`fcntl`); on Windows, lint and test in WSL. Machine-specific paths and live-instance details are in `CLAUDE.local.md` (not committed).

```bash
python -m venv .venv && .venv/bin/pip install -r requirements_test.txt   # Linux/WSL/macOS
ruff format . && ruff check .
pytest -q                                                       # all tests
pytest -q tests/test_forecast.py::test_planning_horizon_end     # single test
```

CI (`.github/workflows/validate.yml`) runs hassfest, HACS validation, ruff and pytest on Python 3.14. `hacs.json` declares minimum HA 2025.6.0 (needed for config subentries).
