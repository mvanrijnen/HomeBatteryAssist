# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

HomeBatteryAssist is a **Home Assistant custom integration** (not an add-on/Docker container), distributed via HACS, that monitors home batteries and the energy flows of a home, and forecasts consumption, prices, PV and battery behaviour (read-only in the current development phase; controlling batteries is the goal; forecasts are verified afterwards). Comparable project: Omnibattery (`ffunes/Omnibattery`).

- **Read-only in the current development phase, by decision of the project owner (until further notice): HomeBatteryAssist does not control batteries or any other device yet** (design everything for control later; user-facing text says "for now" / "in this phase", never "never") — no commands, no state-changing service calls, no control configuration, no own connections to devices that could compete with their integrations (e.g. Marstek Venus v3 allows only one Modbus TCP client; Omnibattery must keep running). Exception agreed by the owner: grid meters may be read directly when that is passive or uses a read-only interface open to any number of clients, and never changes a meter setting (`engine/devices/meters/discovery.py`: HomeWizard P1 API v1, SMA Speedwire multicast). Scope: read inputs, forecast, and verify forecasts afterwards against what actually happened.
- Domain `homebatteryassist`, display name **HomeBatteryAssist**, single config entry (`single_config_entry` in manifest).
- Built incrementally. Batteries are linked through entities of their own integration (`engine/measure/battery_monitor.py`), helped by profiles that recognise batteries other integrations already expose (`engine/devices/batteries/recognition.py`). Network discovery of devices is deferred.
- Forecasts are **not** made by this integration; it consumes them from other integrations.
- Will be published: keep README, `docs/` (details per topic; README is the overview with links), user-facing text and translations release-quality. Repo: https://github.com/mvanrijnen/HomeBatteryAssist (public, alpha: no GitHub releases until the user says so; branch `main`). License: MIT (`LICENSE`).

## Architecture

The package root holds what Home Assistant needs (`__init__.py`, `config_flow.py`, `services.py`, `diagnostics.py`, platform files, `output/` entities, `frontend/` panel, translations). All backend logic is in **`engine/`**, organised in layers with a one-way data flow (`docs/architecture.md`). A layer only imports lower layers:

```
engine/devices (1) -> engine/sources (2) -> engine/measure (3) -> engine/history (4)
  -> engine/forecast (5) -> engine/planning (6) -> engine/evaluation (7)
engine/explain (8) is used by all; engine/coordinator.py runs one forecast cycle
```

**Devices are drivers** (`engine/devices/`, part of the code; one file per brand / type); **everything else that is swappable is a module** (built-in in its layer, own ones loaded from `/config/homebatteryassist/<kind>/` by `engine/own_modules.py`, keyed `custom_<key>`). Every extension point has `base.py` (interface), `template.py` (example, never registered) and one file per built-in variant. Every driver/module/profile has `verified` (default False; True only after a real test); every place it is chosen shows "(not tested)" / "(niet getest)" until then (`config_flow.untested`/`_own_label`; built-in option translations checked by `tests/test_untested_labels.py`), own modules included.

`__init__.py` only wires the parts of a config entry into `HomeBatteryAssistData` (`models.py`, on `entry.runtime_data`). Root platform files (`sensor.py`, `button.py`) only delegate to `output/`. `async_setup` registers the actions (`services.py`) and the sidebar panel (`output/panel.py` + `frontend/panel.js`, websockets `homebatteryassist/status` and `/history`) once per HA start; HA only runs `async_setup` when a config entry exists, so the panel appears after the integration is added.

- **1 `engine/devices/`** — drivers, read-only.
  - `batteries/`: `base.py` = `BatteryModel` (a type by inheritance brand → range → type, e.g. `marstek/__init__.py` → `marstek/venus.py` → `marstek/venus_e_v3.py`; specs used as starting values; `MODELS`, `model_for(device model)`) and `BatteryReader` (one integration's entities, `integrations/omnibattery_integration.py`, `integrations/marstek_modbus_integration.py`, verified; `integrations/victron_gx_integration.py` (core `victron_gx`, not tested; also a grid MeterProfile; `victron/gx_direct_modbus.py` prepared); its `BatteryProfile` recognises batteries; telemetry by translation key; `command()` reads the command the battery has now from its controlling integration (`BatteryCommand`: force mode + charge/discharge power when RS485 control is on, allow switches, hysteresis; `EntityReader.command_entities`); write methods exist but are NEVER called). `recognition.py` `find_battery_candidates` scans the entity registry (never the network). `virtual.py` = the virtual battery simulator (a round every `react_interval_s` (default 5 s), NOM on the time-weighted average over the round (`react_average`), an extra round at once on phase overload, peak or a grid jump ≥ `react_jump_w` (`react_jump`); follows the plan; phase protection `relieve`, phase caps `cap_powers`, peak shaving). A virtual battery can be the **twin** of a real battery (`twin_of`, `BatteryConfig.as_twin_of`): the real one's properties, starts at its SoC (button *Sync with the real battery* → `BatteryInput.sync_twin`), planned in its place (`BatteryInput.plan_states()` excludes twinned real batteries: coordinator, plan check, phase sensors, panel), simulated on the grid without the real battery (`_flow` / `without_batteries`); sensor `twin_difference_today` (value today twin − real), `battery_value_today` per battery (`days[].value`).
  - Direct battery drivers (PREPARED, NOT USED; `enabled = False`, never offered, write methods never called): `batteries/direct/` (`DirectBatteryDriver`, `modbus_driver.py` `ModbusBatteryDriver` with `Point` register maps, `http_driver.py` `HttpBatteryDriver`, `mqtt_driver.py` `MqttBatteryDriver`), one per brand next to its models (`marstek/venus_direct_modbus.py`, `anker/solarbank_direct_modbus.py`, `huawei/sun2000_direct_modbus.py`, `zendure/solarflow_direct_http.py`, `sessy/sessy_direct_http.py`, `indevolt/flex_direct_http.py`, `hoymiles/smiles_direct_mqtt.py`; `DIRECT_DRIVERS`); own Modbus TCP client `devices/transports/modbus_tcp.py`. Device facts from Omnibattery (GPL-3.0) as facts only — never copy its code (HBA is MIT). Each driver declares its control needs (`refresh_s`, `min_interval_s`, `deadband_w`, `idle_is_release`, limits).
  - `inverters/` (PREPARED, NOT USED): PV inverter drivers for the export limit (`InverterDriver`, `points` it would write, `enabled = False`, `async_set_limit` never called/implemented; `sma_home_manager.py` = with a Home Manager the limit belongs to the SHM (Modbus unit 2, 40016 % of PMAX, export), `sma_modbus.py` = older TL types (40023 % x 100), `sma_storage_x.py` (40210/40212, fallback 41193/41195); per-type table in docs/drivers.md; `Point.unit`; all unverified; `victron_gx_feed_in.py` = Victron ESS max feed-in 2706 (export); `sunspec_modbus.py` = any SunSpec inverter, model 123 WMaxLimPct/RvrtTms/WMaxLim_Ena as offsets (chain walked from 40000), unverified); PV subentry optional `possible_sensor` (what it could produce, e.g. via HA Modbus): `PowerFlow.pv_possible_w`/`pv_potential_w`/`pv_curtailed_w`, history records the potential PV (learning), house stays measured; PV subentry fields `inverter_driver` / `inverter_address`. Export limit: `planning/export_limit.py` (0 W below `export_limit_price`, else `export_limit_max_w`, else the connection), live in `control/export_limiter.py` (`ExportLimiter`, `CONTROL = False`, on `BatteryInput.grid_planned_w()`; *Why* `export_limit_started`/`_ended`), sensor `export_limit` (*Max export*) on the grid device.
  - `meters/`: one file per brand — `homewizard.py` (P1 + kWh, API v1, verified), `homewizard_v2.py` (API v2 websocket push, token from HA's HomeWizard entry, never created; not tested), `sma.py` (Speedwire multicast, receive only, verified; discovery only listens 3 s, patched out in tests), `shelly.py`, `iammeter.py` (from API docs, unverified); `direct_reading.py` = `DirectMeter`/`PollingMeter` (stale after 10 s → listeners told); `discovery.py` = `find_direct_meters` / `create_meter`; `__init__.py` `DRIVERS` (also PV sources: subentry `pv_driver` + `pv_address`); `via_ha_integration.py` = meters via their HA integration (`MeterProfile`, HomeWizard P1 verified; config flow step `meter`).
- **2 `engine/sources/`** — modules for external data.
  - `prices/`: `PriceDriver` (find sources / async_read(source, role import|market|export) / watch), `DRIVERS`; `price_points.py` = `PricePoint` + `parse_price_forecast`; DynTarNL verified (roles import/market/export; export from `export price now` `prices` + `forecast_export` (DynTarNL >= 1.2.0, detected by the attribute), else market − `purchase_fee`); action drivers (Nord Pool, EnergyZero, easyEnergy, cached 1 h) and sensor-attribute drivers unverified; `in_development/` (e.g. Tibber) is never offered. Options `price_source` (`<driver>:<source>` or `sensor`), `price_extension`.
  - `pv_forecasts/`: `PvForecastSource`; `solar_forecast_integrations.py` wraps `energy_dashboard_platform.py` (Energy dashboard solar forecast platforms); option `pv_forecast_entries` holds `<key>:<id>` or a plain config entry id (= energy); final check drops invalid values.
  - `weather/` (optional) = weather source modules: `WeatherSource(settings: WeatherSettings(entity_id, api_key, location))` -> `temperature_now`, `async_forecast` (°C per UTC hour, `checked_forecast` final check; `daily_curve` + `combine` fill the days after the hourly forecast with a min→max course); built-in `weather_entity` (`ha_weather_entity.py`, `weather.get_forecasts` hourly + daily, cached 30 min), `knmi` (`knmi_integration.py`, finds the ha-knmi entity), `weerlive` (`weerlive_api.py`, API key, ≤ 300 req/day, every 30 min), `open_meteo` / `open_meteo_knmi` (`open_meteo.py`, no key; `knmi_seamless`); place = HA home rounded to 2 decimals unless `weather_location`; own ones in `/config/homebatteryassist/weather_sources/`. Options `weather_source`, `weather_entity`, `weather_api_key`, `weather_location`, `outdoor_temperature_sensor`.
  - `tariffs/`: `Tariff` turns source prices into what a kWh costs/earns (`apply_tariff`, after the window/correction step, before planning; market prices when `needs_market`); price accuracy stays on source prices.
- **3 `engine/measure/`** — `house_measurement.py` `MeasurementInput` (event-driven): `house = Σ grid phases + Σ PV − Σ excluded − Σ battery power`, floored at 0; grid per phase from sensors (signed, or import − return) or a direct meter (entity listeners throttled to 10 s); unknown grid → consumption unknown. `battery_monitor.py`: `BatteryConfig`, `BatteryState` (`power_w` **+ charging / − discharging**), `BatteryInput` (counters, realised value incl. `value_kwh` for wear, last full charge, activity explanations as periods, one message after start-up; `days` = counters at each local day start → `today()` and `efficiency()` = measured round trip of a real battery over ≤ 30 days once ≥ 1 capacity charged, sensor `battery_efficiency_measured`). `spike_filters/` = spike filter modules (`SpikeFilter.update(when, house_w)` -> `SpikeState(ignore_w, ended_wh)`, stream with own state, `checked` final check; built-in `short_peaks`: rise > threshold above a slow baseline, over within max duration; own ones in `/config/homebatteryassist/spike_filters/`), run by `MeasurementInput`; `nom_balance` = what NOM asks of the batteries (never discharges for excluded devices or ignored peaks); `plan_balance` = a plan per slot with the real solar surplus instead of the forecast one: an unexpected surplus stored on top, a planned charge from missing sun not taken from the grid (`unexpected_surplus`/`unexpected_shortage`, `solar_surplus_w`, threshold option `pv_deviation_w` default 300 W; used by the virtual batteries and the commented control loop). `history/spikes.py`: `spike_w` per record, regular peaks (weekday+hour, ≥ half of the days in 4 weeks) stay in the average and are covered; options `spike_no_discharge`, `spike_exclude_average` (both default on), `spike_threshold_w`, `spike_max_minutes`, `spike_filter`. `engine/units.py`: `state_to_watts`, `parse_float`, `parse_time`.
- **4 `engine/history/`** — `consumption_history.py` `ConsumptionHistory` (time-weighted average per clock-aligned 5/15/60-min interval, `coverage`, `excluded_w`, `pv_w`, `battery_w`, phases; 28 days; invalid stored records skipped), `history_import.py` (action `import_history`), `temperature_import.py` (at start: past records get `temp_c` from the outdoor sensor's statistics and the zones' `w`/`in`/`out` from their sensors' statistics, so the temperature effect is learned at once), `weekday_hour_profile.py` (charts).
- **5 `engine/forecast/`** — **every forward calculation first determines the `PlanningWindow` (`planning_window.py`) and never calculates beyond `window.end`.** `consumption_forecast.py` runs the chosen consumption forecaster module (`forecasters/`: `weekday_hour_profile.py` recency-weighted weekday/hour profile, `same_time_last_weeks.py` last weeks; `raw_forecast` replaces invalid values by the profile) → temperature step (`temperature_effect.py`, optional: W per heating/cooling degree learned from daily means, heating point = room − learned gain, per zone (`measure/heating_zones.py`: heating/cooling subentry with optional `indoor_temperature_sensor`/`outdoor_temperature_sensor`, history `zones`) or the house; applied as the difference with the usual degrees per day of the week and hour (recency-weighted, as the profile; room temperature: half-life 7 d, per hour for working days together + weekend or per weekday, whichever predicted the last week better (`_room_means`)); skipped when a forecaster sets `uses_temperature`) → correction → user adjustments (`user_adjustments.py`: factor/offset/power or `energy_kwh` extra or `part` of the day (`rebalance_parts`); dashboard dialog *Occasional consumption* (toolbar button) via websockets `adjustment_save`/`adjustment_delete` in `output/adjustments_ws.py`); `phase_shares.py` learns the phase shares and per phase the current besides the power (`reactive`, median of history `phase_q`, worked out per reading by `consumption_history.reactive_w` (measured voltage, whole-amp rounding not counted), never from interval averages; loads = signed hypot(load, Q)). Phase protection works on current: `PowerFlow.phase_amps`/`phase_load_w` (measured current; else P / (V × pf); else P / 230 V); meter drivers return `PhaseReading(phase_w, phase_a, phase_v, phase_pf)`; optional grid `current_l1..3` / `voltage_l1..3` sensors; the virtual batteries convert battery power with the phase voltage (`_nominal_devices`).
- **6 `engine/planning/`** — planner modules (`planners/`: `zero_on_meter.py` nom/manual/time_slots via `follow`, `arbitrage.py` DP with fractional-level discharge, cycle limit, peak shaving). `battery_plan.plan_batteries` builds `planner_input` and **always** runs `finalise` (power/phase limits, min/max SoC per battery (`PlannerBattery.members`, `_share`), price rules except user-set fixed actions; SoC/grid/costs). Reserves: `reserve_soc` (always), `night_reserve_soc` (slots outside the day's first..last sun slot, `night_starts`, PV >= `SUN_W`; per-slot `reserve_wh`, `reserve_due` at sunrise: arbitrage DP penalises a missing reserve so it grid-charges before; NOM only holds), `peak_reserve_soc` (`peak_floor_wh`, with a peak limit: below it only import above the peak; `planners/base.discharge_room` used by NOM, arbitrage and `finalise`; virtual batteries raise their target floor, `ForecastData.night_at`). Periodic full charges (`full_charge.py`) are scheduled before planning and passed as `PlannerInput.forced` (W per slot start); `finalise` adds them (fixed, no price rule). `phase_limit.py` (fuse × 230 V × (1 − margin)), `battery_distribution.py` (several batteries; option `charge_order` sequential (default: emptiest first at full power, next only for the rest) or parallel, used by the virtual batteries, `finalise` `_share` and full charge scheduling; a forced full charge goes to its own battery first via `PlannerInput.forced_by`), `time_slots.py` (time slots). Failing own planner → `planner_failed`, nom used (`plan_fallback`, `ForecastData.selected_plan`).
- **7 `engine/evaluation/`** — `forecast_accuracy.py` `ForecastAccuracy` (raw predictions per lead-time bucket settled against measured consumption, PV and later prices; half-life 7 d; learned/off/manual corrections; extra kinds `consumption@<key>` per forecaster and `pv@<key>` per PV correction for the comparison tables); `pv_corrections/` = PV correction modules (`PvCorrector`, `apply_pv_correction` with final check; built-in `hour_and_level` (default: lead factor × per local hour × per level vs the most forecast at that hour) and `lead_time` (original); own ones in `/config/homebatteryassist/pv_corrections/`; option `pv_corrector`; manual/off correction mode → lead time only); `price_surprise.py` (published prices ≥ 0.08/kWh and ≥ 25 % off the estimate the plan used → *Why* `price_published_differs`; price bias uses errors capped at 3× the median error); `plan_check.py` (plan per slot vs the battery counters, both after wear; *plan followed* per slot, apart for real and virtual batteries by capacity share: `followed_pct`, `days()`, `followed()`); accuracy kind `heating` (the temperature step's expected heating/cooling W vs the measured devices, measured only, no correction); `command_check.py` (`CommandCheck`/`CommandMonitor`, every 15 s per real battery: command ≥ `command_check_w` (default 100 W) and < half followed for `command_check_minutes` (default 2) → *Why* `battery_not_following` (+ `_ended`, notify kind `battery_command`, binary sensor `battery_not_following` per battery, panel `command`), or `_explained` with a reason (full/empty/switched off/hysteresis, no alarm); the commented control loop releases a battery with `problem`); `unexpected_surplus.py` (measured PV surplus vs the forecast for this hour while it happens, both ways: ≥ `pv_deviation_w` more and < half forecast → *Why* `pv_surplus_unexpected`; ≥ `pv_deviation_w` forecast and < half there → `pv_shortage_unexpected`; after `pv_deviation_minutes` (default 5), `_ended` after 10 min; two checks wired in `__init__.py` on the measurement listener; notify kind `solar`).
- **8 `engine/explain/`** — `DecisionLog` (messages in `messages.py` incl. `TERMS` phrases, nl/en, every key in all languages — tested; last 200 persisted; event `homebatteryassist_decision`), `plan_story.py` (the plan as periods, compared with no battery), `plan_phases.py` (the plan as phases per kind: discharge, charge_grid, charge_pv, grid_only; current and next with minutes, kWh, price, reason; sensors `phase_*` on the main device and per battery by capacity share), `notifications.py`, `money.py` (`format_money`: amounts in HA's currency `hass.config.currency`; generic c/ct/cent = hundredths of it in `units.price_unit_factor`).
- **`engine/control/`** — BUILT, NOT ACTIVE: `battery_controller.py` (`BatteryController`, pure `decide()`): master switch off by default (`ControlDisabled`), always release (stop/error/watchdog 2 min/switch-off), refresh, throttle + deadband, idle = release, limits. Nothing creates or enables a controller. `control_loop.py` = the control loop written out AS COMMENT ONLY (`ReaderDriver` adapter for readers, `ControlLoop` with the virtual batteries' target steps, SoC floor/ceiling; activation steps in its docstring; commented wiring in `__init__.py`); `tests/test_read_only.py` checks it has no active code. `control_test.py` = test control per real battery (buttons *Test: charge/discharge/stop*, numbers test power/duration, status sensor; `output/control_test.py`, platforms button/number/sensor on the battery's subentry) through `reader_driver.py` (`ReaderDriver`, shared with the loop) and `BatteryController`; switched off by `CONTROL_TEST_ALLOWED = False` (tested): a press only logs `control_test_blocked`. `interceptors/` = interceptor modules (the user's last say per battery before a command: `Interceptor.intercept(InterceptInput)` -> `InterceptResult(decisions: Decision(battery_id, approve|limit|reject|release, power_w, reason), redistribute)`; `run_interceptor` enforces: limit = at most the proposal in the same direction, nonsense/failure = approved, redistribution to approved batteries; built-in `none`; own ones in `/config/homebatteryassist/interceptors/`; option `interceptor`), run by the virtual batteries between peak shaving and `_phase_limited` (HBA's own check after it always wins); *Why* `interceptor_changed`/`_cleared`/`_failed`.
- **`engine/coordinator.py`** — `ForecastCoordinator` runs a cycle: read inputs, window, accuracy, consumption, tariff, plans of every mode/planner, full charges, explanations; `price_log` for the chart.
- **`output/`** — entities (battery devices per subentry; a *Grid connection* device `{entry_id}_grid` with the grid/phase flow sensors and the *Test inputs* button → `engine/explain/input_report.py` persistent notification; totals, sensors) and `panel.py` (websocket data for the dashboard).
- **Icons** — `brand/icon.png` (+ `@2x`, `dark_`); `icons.json` gives every entity/action an MDI icon. `images/icon.png` is the README copy.
- **Technical logging** — `_LOGGER = logging.getLogger(__name__)` everywhere; `diagnostics.py` includes the state of each part and the active/own modules.

### Configuration model

- `entry.data` (fixed, config flow steps 0–3; step 0 `meter` only when a known meter is detected): `phases` (1/3); `max_current_per_phase`, restricted by `MAX_CURRENT_OPTIONS` (1x10/25/35A, 3x25/35/50/63/80A; defaults 1x35A, 3x25A); `sensor_l1..l3` + optional `return_l1..l3`.
- `entry.options` (step 4 `settings` and the options flow, same `settings_schema`): `history_interval`, `planning_horizon_days` (1–7, default 2), optional `price_forecast_entity`, optional `pv_forecast_entries` (list of config entry ids; field only shown if a solar forecast integration is loaded); the other settings are grouped in collapsible sections by `SETTINGS_SECTIONS` (export, solar incl. `pv_corrector`, planning, limits, spikes, full charge, temperature (battery), notifications, weather). A new setting needs: the schema field, `settings_from_input`, its section, and texts in all three translation files.
- Subentries (any number, added under the integration in the UI, with reconfigure): `pv_source`, `excluded_load` (e.g. EV charger) and `heating_cooling` (part of the house, recorded apart as `heating_w`) with `name`, `sensor`, `phase` (`none`/`l1`–`l3`; field only on 3-phase); `battery` with step `user` (pick a detected battery or `manual`; skipped when nothing is detected) → `battery` (sensors and properties, prefilled from the profile); reconfigure uses the battery form. `sensor_conflict` ensures every sensor is used once (grid or one subentry).
- Any options or subentry change reloads the entry (update listener). Unload awaits `HouseConsumption.async_stop()` so history is saved before the reload reads it.
- Every new config text must be added to `strings.json`, `translations/en.json` (identical copy) and `translations/nl.json`. Custom integrations can't use `[%key:...%]` references — write literal text.

## Documentation site

`docs/` is also a bilingual MkDocs Material site (`mkdocs.yml`, mkdocs-static-i18n, suffix structure): every page exists as `page.md` (English, also read on GitHub) and `page.nl.md` (Dutch). **Change both languages together.** Dutch headings keep the English anchor (`## Uitleg {#explanation}`); anchors are GitHub-style (`pymdownx.slugs`), so links work on GitHub and on the site. Use Markdown images (not raw HTML) so the Dutch pages resolve them. `docs/reference*.md` is generated from the translations by `scripts/docs_reference.py` (CI fails when it is stale: rerun after changing a text). `docs/javascripts/language.js` opens the reader's language (browser language, then the remembered choice). `.github/workflows/docs.yml` publishes to GitHub Pages on every push to `main` (https://mvanrijnen.github.io/HomeBatteryAssist/); `validate.yml` builds it as a check. Build locally: `pip install -r requirements_docs.txt && mkdocs serve`.

## Commands

Home Assistant's test harness does not run on native Windows (`fcntl`); on Windows, lint and test in WSL. Machine-specific paths and live-instance details are in `CLAUDE.local.md` (not committed).

```bash
python -m venv .venv && .venv/bin/pip install -r requirements_test.txt   # Linux/WSL/macOS
ruff format . && ruff check .
pytest -q                                                       # all tests
pytest -q tests/test_forecast.py::test_planning_horizon_end     # single test
```

CI (`.github/workflows/validate.yml`) runs hassfest, HACS validation, ruff and pytest on Python 3.14. `hacs.json` declares minimum HA 2025.6.0 (needed for config subentries).
